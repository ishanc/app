1. SYSTEM OVERVIEW
================================================================================

PURPOSE:
--------
This system transforms SumTotal Learning Management System (LMS) data into CSOD 
(CSO Direct) format using Neo4j database-driven mapping rules. It provides a 
web interface for file upload and automated data transformation.

KEY FEATURES:
-------------
- Web-based file upload interface
- Database-driven mapping rules (no code changes needed)
- Support for Excel (.xlsx) and CSV files
- Automatic field mapping and transformation
- Real-time processing with immediate download
- Docker containerization for easy deployment
- Comprehensive logging and error handling

SUPPORTED FILE TYPES:
---------------------
- Activity files (Curriculum, Tests, Sessions, etc.)
- Core files (Employee, Organization, Jobs, etc.)
- Prerequisites files (Facility, Instructor, Subject, etc.)
- Transcript files (various completion records)

5. DATABASE SCHEMA
================================================================================

NEO4J GRAPH MODEL:
------------------

NODES:
------
- File: Represents file types (e.g., "Activity_Curriculum")
- SumTotalField: Source fields from SumTotal data
- CSODField: Target fields for CSOD format
- Transformation: CASE statement transformation rules

RELATIONSHIPS:
--------------
- (File)-[:OUTPUTS_FIELD]->(CSODField)
- (File)-[:HAS_FIELD]->(SumTotalField)
- (SumTotalField)-[:MAPS_TO]->(CSODField)
- (CSODField)-[:HAS_TRANSFORMATION]->(Transformation)

FIELD PROPERTIES:
-----------------
CSODField properties:
- name: Field name
- mandatory: "Mandatory" or "Optional"
- field_type: Data type (char, int, etc.)
- char_length: Maximum character length
- default_values: Default value if no source data
- accepted_values: Allowed values
- transformation: CASE statement transformation rule

EXAMPLE QUERY:
--------------
```cypher
MATCH (f:File {name: "Activity_Curriculum"})-[:OUTPUTS_FIELD]->(csod:CSODField)
OPTIONAL MATCH (st:SumTotalField)-[:MAPS_TO]->(csod)
OPTIONAL MATCH (f)-[:HAS_FIELD]->(st)
RETURN csod.name, st.name, csod.default_values, csod.transformation
```

ENDPOINTS:
----------

GET /
-----
- Purpose: Main web interface
- Response: HTML page with file upload form

POST /upload
------------
- Purpose: Upload and process file

- Parameters:
  - file: Excel or CSV file
- Response: JSON with processing status
- Success: {"message": "File successfully processed", "processed_file": "filename.csv"}
- Error: {"error": "Error description"}

GET /download/<filename>
------------------------
- Purpose: Download processed file
- Parameters: filename (from upload response)
- Response: CSV file download

GET /files
----------
- Purpose: List available processed files
- Response: JSON array of filenames

DELETE /delete/<filename>
-------------------------
- Purpose: Delete processed file
- Parameters: filename
- Response: JSON success/error message

ERROR CODES:
------------
- 400: Bad Request (no file, invalid file type)
- 500: Internal Server Error (processing failure)

7. FILE PROCESSING LOGIC
================================================================================

FILENAME MAPPING:
-----------------
The system maps incoming filenames to database keys using a predefined mapping:

Activity Files:
- Activity_Curriculum → Activity_Curriculum
- Activity_QuickAssessment → Activity_Test
- Activity_ILTSessions → Activity_SessionParts
- Activity_ILTClass → Activity_Sessions
- Activity_ILTCourse → Activity_Events
- Activity_OnlineCourse → Activity_OnlineCourse
- Activity_Document → Activity_Material

Transcript Files:
- Transcript_Curriculum → Transcript_Curriculum
- Transcript_Document → Transcript_Materials
- Transcript_ILTClass → Transcript_Sessions
- Transcript_OnlineCourse → Transcript_OnlineCourse
- Transcript_QuickAssessment → Transcript_Tests

Core Files:
- Core_Audience → Core_Audience
- Core_Domain → Core_Domain
- Core_Employee → Core_Employee
- Core_Jobs → Core_Jobs
- Core_Organization → Core_Organization

Prerequisites Files:
- Prerequisites_Facility → Prerequisites_Facility
- Prerequisites_Instructor → Prerequisites_Instructor
- Prerequisites_Provider → Prerequisites_Provider
- Prerequisites_Question → Prerequisites_Question
- Prerequisites_QuestionBanks → Prerequisites_QuestionBanks
- Prerequisites_Subject → Prerequisites_Subject

PROCESSING STEPS:
-----------------
1. File Upload: Validate file type and size
2. Filename Mapping: Convert to database key
3. Rule Fetching: Get mapping rules from Neo4j
4. Data Reading: Load Excel/CSV with pandas
5. Transformation: Apply mapping rules and transformations
6. Output Generation: Create CSOD-formatted CSV
7. File Storage: Save to processed folder
8. Response: Return download link

DATA TRANSFORMATION LOGIC:
-------------------------
For each field in the mapping rules:

1. If SumTotal field exists and has data:
   - Use SumTotal value
   - Apply transformation if specified
   
2. If SumTotal field is empty or doesn't exist:
   - Use default value if specified
   - Otherwise leave empty

3. Apply field constraints:
   - Character length limits
   - Data type validation
   - Mandatory field checks

8. TRANSFORMATION RULES
================================================================================

CASE STATEMENT PARSING:
-----------------------
The system parses Cypher CASE statements for field transformations:

Example CASE statement:
```cypher
CASE 
  WHEN input_value = 'Artificial Intelligence' THEN '1274'
  WHEN input_value = 'Machine Learning' THEN '1275'
  ELSE '0'
END
```

Parsing Logic:
- Extracts conditions and values
- Handles input_value placeholders
- Supports ELSE clauses
- Pattern matching for partial matches

TRANSFORMATION TYPES:
--------------------
1. Direct Mapping: SumTotal field → CSOD field
2. Value Transformation: CASE statement with conditions
3. Default Values: Fallback when no source data
4. Field Constraints: Length limits, data types

SPECIAL HANDLING:
-----------------
- Provider Type: Automatically maps to 'ILT' or 'ONLINE'
- Character Length: Truncates fields exceeding limits
- Numeric Values: Handles float/integer conversions
- Empty Values: Converts NaN to empty strings

NiFi Flow Design:
```
Error Event → ListenHTTP → EvaluateJsonPath → PutDatabaseRecord → RouteOnAttribute → Success/Failure Routes
```

Detailed Flow:
1. ListenHTTP (port 8080)
   - Receives error events from applications
   - Endpoint: /error-log
   - Accepts JSON error payloads

2. EvaluateJsonPath
   - Extracts error details from JSON
   - Fields: error_id, message, category, timestamp, file_name, line_number, stack_trace

3. PutDatabaseRecord
   - Inserts error records into MySQL error_logs table
   - Uses connection pooling for efficiency
   - Handles database failures gracefully

4. RouteOnAttribute
   - Routes errors based on category and severity
   - CRITICAL → Notify (email/Slack)
   - WARNING → LogAttribute (console logging)
   - INFO → LogAttribute (console logging)

5. PutFile (backup)
   - Saves error files to disk for backup
   - Directory: /errors/backup
   - Filename: ${now():format('yyyy-MM-dd-HH-mm-ss')}-${error_id}.json

```python
import requests
import json

def log_error_to_nifi(category: str, message: str, file_name: str = None, 
                     line_number: int = None, include_stack_trace: bool = True):
    """Log error to Apache NiFi"""
    error_payload = {
        "error_id": generate_error_id(),
        "message": message,
        "category": category,
        "timestamp": datetime.now().isoformat(),
        "file_name": file_name,
        "line_number": line_number,
        "stack_trace": traceback.format_stack() if include_stack_trace else None
    }
    
    try:
        response = requests.post(
            "http://nifi-server:8080/error-log",
            json=error_payload,
            timeout=5
        )
        response.raise_for_status()
    except Exception as e:
        # Fallback to console logging if NiFi is unavailable
        logger.error(f"Failed to log to NiFi: {str(e)}")
        logger.error(f"Original error: {message}")
```

15.2 CRITICAL FIELD NAME MAPPING ISSUE DISCOVERY
================================================================================

PROBLEM IDENTIFICATION:
----------------------
During implementation, a critical discrepancy was discovered between completeness 
analysis results and error log data:

**Dashboard Output:**
- Mandatory Completeness: 100.00%
- Incomplete Mandatory Fields: 0

**Error Log Evidence:**
- MANDATORY_EMPTY errors: 29,020
- Total errors: 34,041
- Lines with errors: 11,413

**Contradiction:** Cannot have 29,020 mandatory empty errors AND 0 incomplete mandatory fields.

ROOT CAUSE ANALYSIS:
--------------------

1. FIELD NAME MISMATCH:
   - Excel DataFrame columns: `TrainingStatus` (no space)
   - Neo4j SumTotal fields: `Training Status` (with space)
   - Completeness calculator: `if column in mandatory_fields` fails

2. MANDATORY FIELD DETECTION:
   - Neo4j query correctly identifies 4 mandatory fields
   - Field name comparison fails due to space/underscore differences
   - Result: Mandatory field violations are missed

3. CALCULATION LOGIC:
   - Completeness calculation shows 100% due to missed mandatory fields
   - Error logger correctly identifies violations
   - System inconsistency between validation and completeness analysis

TECHNICAL DETAILS:
------------------

**Excel DataFrame Columns:**
```
EmployeeID, ActivityCode, TrainingStatus, RegistrationDate, CompletionDate, DueDate, Score, Notes
```

**Neo4j SumTotal Field Names:**
```
EmployeeID, ActivityCode, Training Status, RegistrationDate, CompletionDate, DueDate, Note
```

**Mandatory CSOD Fields (from Cypher):**
```
User ID*, Curriculum ID*, Transcript Status*, Request Date/Time*, Registration Date/Time*
```

**Field Name Mismatches:**
- `TrainingStatus` vs `Training Status` (space difference)
- `Notes` vs `Note` (singular vs plural)

15.3 SOLUTION: ERROR LOG-BASED COMPLETENESS CALCULATION
================================================================================

PROPOSED SOLUTION:
-----------------
Instead of recalculating completeness from scratch, use the **already validated 
error log data** for completeness calculations:

**Advantages:**
1. Eliminates field name mapping issues
2. Uses validated data (error logs are source of truth)
3. Simpler and more reliable
4. Consistent with validation system
5. No complex field name normalization needed

IMPLEMENTATION APPROACH:
------------------------

**Current Error Log Data:**
- `nulls_found`: 29,020 (from MANDATORY_EMPTY errors)
- `total_records`: 11,413
- `mandatory_fields`: 4 (from Neo4j)

**Completeness Calculation:**
```python
total_mandatory_positions = mandatory_fields * total_records  # 4 * 11,413 = 45,652
filled_mandatory_positions = total_mandatory_positions - nulls_found  # 45,652 - 29,020 = 16,632
mandatory_completeness = (filled_mandatory_positions / total_mandatory_positions) * 100
# Result: (16,632 / 45,652) * 100 = 36.4%
```

**Expected Results:**
- Mandatory Fields: 4
- Incomplete Mandatory Fields: 29,020
- Mandatory Completeness: 36.4%

ISSUE DISCOVERY:

During anomaly report implementation, a critical data loss issue was discovered

PROBLEM DESCRIPTION:
--------------------

**Symptoms:**
- Input Topic field: 100% populated (1691/1691 records) ✅
- Output Topic field: 16.7% empty (282/1691 records) ❌
- Anomaly report discrepancy: 100% completeness vs MANDATORY_EMPTY errors

**Root Cause Analysis:**
The transformation pipeline is losing data between input_df and output_df:

```
Input DataFrame (Topic field) → [TRANSFORMATION PROCESS] → Output DataFrame (Topic field)
     100% populated                    DATA LOSS OCCURS              16.7% empty
```

**Technical Details:**

1. **File:** lasVegas/app/sumtotal_transformer_with_neo4j.py
2. **Function:** transform_sumtotal_file() lines 343-367
3. **Process Flow:**
   ```python
   # Line 351: Copy from input to output ✅
   process_source_field_mapping(input_df, output_df, rule, populated_fields)
   
   # Line 354: Apply transformations ❌ POTENTIAL DATA LOSS

   # Line 357: Apply defaults ❌ LEAVES MANDATORY FIELDS EMPTY

   ```
